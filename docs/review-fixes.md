# 系统性 Review 修复记录

[项目概览](../README.md) · [存储契约](storage.md) · [API 契约](api.md) · [开发与回归](development.md)

## 基线与范围

评审基线为 `5c0d3fd15ff54ea3447c9220a7a87a80f7c0bde1`。本轮面向开发中的当前版本，落实 R-001 至 R-016，并将存储格式升为 **12**。旧格式数据库保持原样，新环境直接初始化新结构；完整搬迁与备份恢复以相同当前格式为边界。本轮没有部署到业务数据库。

目标是关闭已确认问题、对原有风险建立可执行的边界和回归，而不是宣称不存在其他缺陷或达到所有负载下的全局最优。生产容量仍应按部署 CPU、内存、几何复杂度、数据规模和网络条件验收。

## 可重复的测试入口

传输资源测试位于 [resource_lifecycle.rs](../crates/server/tests/resource_lifecycle.rs)，包括进程内请求取消和真实服务集成中的资源恢复；预算与帧生命周期单元测试位于 [resources.rs](../crates/server/src/resources.rs)。原有 [service.rs](../crates/server/tests/service.rs) 保留 20 路并发、大于 4 MiB 保存与流式传输回归。

数据库专项测试位于 [review_postgis.rs](../crates/engine/tests/review_postgis.rs)，使用受控锁屏障、独立监控连接和可释放的临时触发器。所有写入前验证数据库名为 `geoledger_test`，测试命令由调用方显式启用。性能工作量回归位于 [review_tests.rs](../crates/engine/src/session/review_tests.rs)，不使用易受机器负载影响的固定毫秒阈值替代复杂度和执行计划断言。

```bash
cargo test --locked -p geoledger-spatialite --lib
cargo test --locked -p geoledger-server --test resource_lifecycle
cargo test --locked -p geoledger-server --test service
cargo test --locked -p geoledger-engine --lib review_tests -- --nocapture
cargo test --locked -p geoledger-engine --test review_postgis -- --ignored --test-threads=1
cargo test --locked -p geoledger-engine --lib postgis_hot_spatial_queries -- --ignored --nocapture --test-threads=1
./scripts/check.sh
```

独立 PostGIS 测试要求已安装扩展的可丢弃数据库。测试环境通过 `GL_TEST_DATABASE_URL` 传入；SQLite 使用可信安装路径 `GL_SPATIALITE_EXTENSION`。运行完整入口可同时检查格式、Clippy、引擎/服务端/SDK 回归、备份恢复及可选 PostGIS 测试。

## 资源边界与运行取舍

单请求/响应编码预算默认各 64 MiB，接收/响应总预算默认各 256 MiB。每个请求先取得最小额度；接收帧、数据库结果、分页组装和编码增长前再取得所需额度，拒绝超额增长而不是先分配后计数。gRPC 帧头声明的消息尺寸在解码器 reserve 之前计入。已编码数据交给传输层后，其 Bytes 所有者仍持有相应额度，避免 body EOF 提前解除慢连接预算。

这些额度约束的是编码高水位及并发传输，不是进程 RSS 的字节精确上限；Rust JSON 树、解析副本、原生库和运行时仍需要部署余量。更大的合法要素可通过配置增加上限，但应同步核对总预算和容器资源。本文没有将诊断时间外推为生产吞吐量。

数据库清理期间 active 包含 retiring，二者不能相加计算总名额。回滚确认失败时保留隔离名额；每个池可用一个串行控制连接确认原 backend PID 与启动时间已消失。取消信号存在竞态，特别是 COMMIT 边界；业务方仍通过不可变原发布请求确认最终结果。清理连接和 PostgreSQL 自身资源应纳入部署监控。

冲突缓存是派生数据库状态：首次构建及读取页面都会在项目锁内稳定授权和 HEAD，换取跨实例一致的精确总数与无重复分析。逻辑导出只包含业务版本表，导入自动重建草稿计数并按需重建冲突索引。派生表不作为新的授权边界。

## 验证边界

验证包括静态检查、SQLite/SpatiaLite、隔离 PostgreSQL/PostGIS、受控取消和锁竞态、索引执行计划、虚拟机步骤以及备份恢复。实际容量以 release 构建和部署环境基准为准；长时间网络分区、原生 sanitizer、全链路 RSS 压力与 COMMIT 附近故障注入属于进一步的生产验收范围。依赖供应链的全面审计不因本轮 16 项修复而自动完成。

## 本轮执行记录

验证环境为 macOS / Apple Silicon、Rust 1.92.0、SQLite 3.53.2、PostgreSQL 17.10 与 PostGIS 3.6.4。数据库实验只使用独立临时实例，业务数据库和旧格式数据目录保持原样。

完整检查入口通过格式、全工作区 Clippy、独立 SpatiaLite 测试、引擎/服务端/Rust SDK 测试与备份演练。PostGIS 另行执行 26 项一致性测试、5 项失败/锁竞态测试、热空间计划测试、原表事务、存储、双向导入导出和审计游标测试。两种 DSN 语法各对三类独立数据库夹具执行一次，原连接数据库没有 GeoLedger 表，遗留随机数据库数量为 0。

备份演练经过在线备份、恢复到新目录、逻辑导出和导入，HEAD 保持 r3，11 条审计事件保持一致。显式百万要素容量、长时间模糊测试和额外 TLS 证书矩阵按各自入口执行，不能把默认跳过的测试计为本轮通过。

最终增量检查：完整 `scripts/check.sh` 退出码为 0；新增传输生命周期集成用例 6 项全部通过，包括真实 TLS 的 IP 限流、成功及错误响应的慢消费、取消后的完成计数和 gRPC 解码前拒绝。格式检查、Clippy、文档链接、环境变量契约和备份演练通过。所有变更保留在本地工作区，提交和推送由发布步骤单独处理。
