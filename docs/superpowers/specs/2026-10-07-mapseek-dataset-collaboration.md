# MapSeek Dataset 协作编辑与增量同步设计

日期：2026-10-07。状态：用户已批准并授权直接实施，代码实现与联调验收另行记录。

## 用户目标

在 MapSeek 现有 Dataset 矢量编辑页提供类似 Git 的协作：多人各自编辑、按修改提交、自动合并互不冲突的变化、提示并解决冲突。提交说明可留空。首次把数据下载到浏览器 OPFS，随后打开和同步只获取变化；保留本地未提交修改。

GeoLedger 作为 Rust crate 被 MapSeek 调用，随 MapSeek Rust 服务运行。浏览器继续通过 MapSeek 网关访问，使用既有用户、租户、项目和 Dataset 授权。

## 已核对的实现基础

- GeoLedger 的 [center 库入口](../../../crates/center/src/lib.rs) 已提供 CenterApplication、草稿、版本读取、发布和三方合并；[core 合并算法](../../../crates/core/src/merge.rs) 可复用。
- [center 包](../../../crates/center/Cargo.toml) 同时包含库和 gl-center 二进制。目前 HTTP 依赖与库默认绑定，需要提供纯库构建组合。
- [中心发布](../../../crates/center/src/publication.rs) 已将历史、HEAD、提交和幂等结果置于同一事务。现有存储为中心原生要素集合，需要增加已注册业务表的接入。
- MapSeek 的 `frontend/apps/cloud/src/features/dataset/pages/VectorEditorPage.tsx` 每次打开已有 Dataset 都创建随机草稿 ID，并重新读取全部要素。
- MapSeek 的 `frontend/apps/cloud/src/features/dataset/lib/loom-dataset.ts` 已计算记录和字段增量，但当前提交入口直接修改正式表。
- MapSeek 的 `services/featureserv/internal/infrastructure/catalog/batch.go` 将编辑和缓存刷新 revision 原子提交，可以沿用其事务要求。
- Loom 已具备 OPFS 图层 generation、工程 manifest 提交点、会话 journal 和 Web Locks；具体接入以 MapSeek 锁定的 workbench 包公开接口为准，不直接导入另一个源码仓库的内部文件。

## 方案选择

采用中心协作库嵌入 MapSeek 的 `spatial-engine`。现有 emap/Loom 编辑器继续负责绘制和属性编辑，MapSeek 负责权限及业务表映射，GeoLedger 负责草稿、提交、历史和合并。

另外两条路线是部署独立中心服务，或将本地 SQLite 仓库挂到现有编辑接口。前者增加部署及跨进程提交协调，后者面向共享工作副本和分支切换，均不作为此次路线。

调用关系：

```text
Dataset 编辑页 + Loom/OPFS
    → MapSeek Go 网关：用户认证、Dataset 授权
    → MapSeek spatial-engine 内部适配入口
    → geoledger-center crate：协作应用操作
    → PostGIS：历史 + 正式业务表 + 发布版本/缓存刷新标记
```

Go 和 Rust 之间仍有 MapSeek 内部传输；crate 消除的是独立 GeoLedger 服务。编辑、提交和冲突查询需要即时响应，不经 Temporal 任务轮询。大规模初次登记可以使用现有任务机制，但登记结果必须是可恢复的一致快照。

### crate 边界

- 沿用 `geoledger-center` 的包名及公共应用入口，不另建同功能引擎；把 HTTP、控制台和 gl-center 启动依赖移到可选 feature。
- 增加公开的类型化协作命令、结果和错误，MapSeek 适配层调用应用层，传输层不直接执行版本 SQL。
- 复用 core 的三方合并。MapSeek 的权限、Dataset 表名解析、缓存刷新和业务字段约束留在宿主适配层。
- 提供受控的宿主事务接入：宿主业务表写入与 GeoLedger 发布共享同一连接、事务和截止时间。失败整体回滚；宿主不能绕过应用层单独推进 HEAD。
- 同步库入口在 Rust 异步服务中通过有界阻塞执行调用，保留现有操作期限、容量及超时关闭连接行为；本次不为嵌入而整体改写异步数据库层。
- 本地联调可以使用 path 依赖。可复现构建使用锁定 revision 的 Git 依赖或已发布包版本，不把个人电脑路径作为发布依赖，也不在此次工作中自动发布 crate。

## 领域与一致性边界

通用语言：Dataset、基础版本、工作副本、草稿、提交、远程 HEAD、同步、冲突、解决选择。

每个 Dataset 有独立版本序列和历史入口，不能把其他 Dataset 的变化混入当前数据的同步。中心现有项目修订可继续作为内部序列，公开契约需携带 Dataset 身份与 epoch，并可独立判断 Dataset 是否变化。

不变量：

1. 提交历史、正式业务表、数据内容版本、缓存刷新标记和幂等结果共同成功或共同失败。
2. 保存草稿只改变私有增量；正式地图查询只读取已发布数据。
3. 服务端从可信身份上下文确定作者。浏览器请求正文不决定 subject、tenant 或 project。
4. 服务端从版本历史取得三方合并的 base，客户端不能伪造 base 来覆盖远程修改。
5. 重试同一提交返回原结果；同一 request_id 配不同内容返回冲突。
6. 固定版本分页读完之后才能推进本地版本标识。
7. 更新远程基础数据不能删除、覆盖或提前标记已提交的本地修改。

MapSeek 网关校验 query/update 权限，Rust 入口验证服务间身份、操作授权范围与 Dataset 所属租户/项目，并再次校验资源可编辑状态。历史和变更接口使用同样的资源访问范围。采用既有签名内部请求模式，为协作接口设置独立 audience 并绑定方法、路径、正文与有效期。

## 正式表接入

Dataset 绑定由宿主解析，包含稳定 Dataset ID、租户/项目、物理表、主键列、几何列、SRID、字段结构与注册 epoch。物理表名来自已授权的 Dataset 元数据，经过数据库标识符引用，浏览器不能传任意 SQL 或表名。

首次登记在受控数据库事务或可恢复导入任务中建立一致的初始记录与 schema 历史。先处理存量数据的规模与并发写入，再开放编辑；禁止用会漂移的 offset 分页拼接初始版本。新登记只采用明确的当前格式。

一旦 Dataset 由版本库管理，旧单条编辑、批量编辑和字段编辑入口都必须经过相同版本事务，或明确拒绝旧写入协议并要求使用新协议。不得保留可以绕过历史的正式写入口。直接数据库编辑的管理角色权限和发布服务写角色须分开。

正式表保留原始 SRID、PostgreSQL 字段类型和约束。属性修改不让未改动几何经历坐标往返转换；浏览器 GeoJSON 为 EPSG:4326。历史要保留可无损恢复的数据库值及几何，不能只依赖浏览器解析后的浮点 JSON。

字段新增/删除跟随提交进入 schema 历史。属性缺失、属性值 null 和字段删除是不同操作。删除字段与他人修改该字段构成冲突；字段类型或结构产生歧义时阻止发布并要求解决，不猜测转换。

首次落地覆盖现有编辑器可编辑的普通矢量表；分区表及其他表类型需以宿主适配器能力验证结果明确开放，不能在查询时悄悄降为另一种写入行为。

## 浏览器工作副本

缓存身份包括服务来源、用户 ID、租户、项目和 Dataset ID。相同用户再次打开同一 Dataset 复用稳定的本地工程 ID，停止每次生成新的空白工作副本。

本地保存以下内容：

- `base`：已同步的远程基础数据、schema、epoch 和 revision。
- `working`：Loom 工程及编辑检查点。
- `pending`：相对 base 的新增/修改/删除、schema 修改和本地 generation。
- `sync`：固定目标 revision、下载游标、已持久化分块、提交 request_id 与请求内容摘要。

复用 Loom 的 generation/manifest 提交方式。增量页先写新 generation，所有所需文件持久化后再切换 manifest；中断时继续使用完整旧版本。记录同步游标与基线 revision 必须与对应数据一致，不先写“已更新”再补写记录。

首次快照按页流式下载到 OPFS，支持恢复；后续接收变化记录和删除标记，并更新本地索引与受影响数据。Loom 的 TopoJSON 检查点可能仍需要本地重建，这不等于重新从网络下载全部数据。验收分别衡量网络传输量、本地重建耗时和编辑器内存峰值。

使用工程级 Web Lock 防止多个标签同时写同一个工作副本。第二个标签提示已有编辑窗口，允许只读查看；跨用户/租户切换停止旧请求并关闭当前会话。离开编辑页可保留本地草稿，显式“放弃修改”才删除 pending。持久化失败时不显示“已保存”。

申请浏览器持久存储并显示实际配额错误。缓存被浏览器清理或用户删除后重新初始化；因此“全量下载一次”适用于本地缓存仍在的情形，而非永久存储保证。离线状态只允许基于已有副本继续本地编辑，提交和确认远程最新状态需要联网。

## 同步与提交流程

### 打开和更新

1. 先检查身份与 Dataset 权限，然后读取本地缓存 manifest，并轻量查询远程 HEAD。
2. 没有缓存时获取固定 revision 的初始快照；已有缓存且版本相同时直接打开本地图层。
3. 远程领先时显示“远程有新版本，更新后继续”，提供增量更新入口；不在每次鼠标/绘制操作中请求远程数据。
4. 无本地修改时应用远程增量，原子推进 base。
5. 有本地修改时保留 working/pending，取得远程增量并执行 base/local/remote 三方合并。无冲突时更新基线并保留本地修改；冲突进入解决界面，禁止未经确认的覆盖。
6. 页面重新获得焦点、用户点击同步或准备提交时检查 HEAD。检查后发生的并发修改仍由发布事务重新验证，检查 HEAD 不是锁。

### 提交

1. 固定一次本地编辑 generation，展示新增/修改/删除与字段变化数量；提交说明为可选输入。
2. 只上传相对 base 的变化；草稿上传按字节和记录数分块并可重试，大草稿不等于一次大 HTTP 请求。
3. 新要素带稳定 client_id，服务端一次分配正式主键并持久化映射；重试不重复新增。
4. 每批上传携带幂等标识及期望草稿版本；发布使用单独稳定 request_id 和已完成上传的草稿版本。
5. 服务端锁定对应发布 HEAD，在同一事务内重新执行三方合并、schema/数据库约束校验及正式写入。
6. 无冲突则生成提交；空说明保存为空字符串，作者仍由身份确定；全无变化时不制造空提交。
7. 结果丢失时保留原 request_id 和请求内容，查询或原样重试，不能重新生成 ID 猜测重提。
8. 成功后拉取本地 base 到提交结果 revision 的增量，包含他人已合并变化和新 ID 映射，然后推进本地 base。只清除本次已提交 generation；提交期间的新编辑保留，或在提交期间冻结编辑输入。

### 冲突处理

按要素和字段展示共同基础、本地、远程。不同要素以及同一要素不同属性自动合并；同字段不同值、删除对修改、双方几何修改进入冲突。几何作为整体冲突单元，不自动拼接顶点或猜测拓扑。

用户可选择保留本地、采用远程，或返回编辑器调整。双方修改同一几何时提供地图高亮对比；所有选择在服务端重新验证。选择携带生成冲突时的 HEAD 和草稿版本；远程再次推进时重新计算，保留选择但要求重新确认。取消合并保留原本地工作副本。

## 协作接口契约

以下为应用层语义，MapSeek HTTP 路由与 Rust 类型在实施时统一定义，不能只提供前端 mock。

| 操作 | 核心输入 | 结果与保证 |
| --- | --- | --- |
| head | Dataset scope | epoch、revision、schema revision，响应体不含要素 |
| snapshot | 固定 revision、cursor、字节预算 | 固定版本要素页、schema、next cursor、完成标记 |
| changes | epoch、from、to、cursor、字节预算 | 有序变化及删除标记、schema 变化、固定 to、完成标记 |
| open draft | Dataset、base revision、幂等 ID | 私有 workspace、workspace version |
| save delta | workspace、期望版本、批次 ID、patch/create/delete/schema ops | 新 workspace version、稳定 ID 映射；重复批次返回原结果 |
| preview merge | workspace | base/head/version、自动合并结果、分页冲突 |
| resolve | workspace/version、expected head、choices | 验证后的选择和新草稿版本 |
| publish | workspace/version、request_id、可空说明 | commit revision、ID 映射、变更摘要 |
| commit result | request_id、Dataset scope | 已提交结果或明确待确认状态 |
| history / commit | Dataset、cursor / revision | 作者、时间、说明和分页 diff |

delta 的修改只包含真正改变的属性及可选几何；删除使用显式操作，禁止借由属性缺失推断删除整条记录。changes 返回受影响要素的权威值或明确 patch，与客户端应用逻辑采用同一协议。游标绑定 Dataset、epoch、from/to 及页内位置；重复页可重放，越界和跨资源游标被拒绝。

初次 snapshot 和后续 changes 都遵守展开后响应预算；单条合法大要素能单独传输。现有 16 KiB 要素和 1000 草稿变化限制需要通过真实几何样本和有界执行改造，不能靠一次性提高所有限制替代容量控制。

数据库重新登记产生新 epoch。客户端遇到 epoch 不匹配或缺失历史时先保留本地修改，再提示重新建立基础副本，不能静默丢弃修改或把不同代数据直接合并。

## 格式与范围

新增持久化结构和同步编码需要显式版本。GeoLedger center schema FORMAT_VERSION、不可变对象格式、本地 SQLite STATE_VERSION、浏览器缓存格式和 API 协议版本分别管理；此次按新格式初始化专用验证数据并重新导入源表，保留当前格式的恢复与事务回滚。

本次包含现有 Dataset 编辑、增量同步、可选提交说明、历史查看和冲突解决。分支命名、PR 审批、实时光标、逐顶点协同和栅格版本管理属于后续独立需求。

## 验收

1. 两个真实身份从同一版本打开；修改不同记录或不同属性后都能提交，双方修改保留。
2. 同属性、几何以及删除/修改冲突明确显示；解决后远程再次变化会重新触发确认。
3. 说明留空成功提交；伪造作者、跨租户/项目/数据集以及撤权后的提交被拒绝。
4. 初次下载完成后关闭再打开，同一版本的网络要素下载量为零；远程只改少数要素时只下载这些变化和协议元数据。
5. 本地未提交修改遇到远程变化、刷新、浏览器重启或同步中断仍可恢复。
6. 下载中远程连续提交不导致混合快照；分页中断可续传，重复页和删除标记正确处理。
7. 响应丢失或服务重启后重试不产生重复提交/新增要素；本地基线不提前推进。
8. 字段新增/删除与他人数据编辑保持三方冲突规则，失败回滚正式表、历史和缓存 revision。
9. 多标签、配额不足、写 manifest 失败、缓存丢失和 epoch 变化均有明确状态，不误报成功。
10. 专用 PostGIS 测试数据库验证真实业务表与历史事务；浏览器使用隔离 OPFS 上下文测试，不访问用户已有工程。
11. 以记录数、总字节、最大几何、变化比例分别记录首开、重开、增量同步和提交耗时，覆盖超过 1000 条修改及超过 16 KiB 的合法几何。

## 实施顺序

1. 固定跨仓库命令与类型契约，整理 center 的纯库构建及宿主事务入口。
2. 实现业务表登记、schema 历史、增量读取、可重试草稿上传和原子发布，补充数据库回归。
3. 在 MapSeek Rust 服务嵌入 crate，接通可信内部入口、Go 网关权限及旧写入口约束。
4. Dataset 编辑页接入稳定 OPFS 工作副本、检查 HEAD、快照初始化和增量同步。
5. 接入可选提交说明、历史与冲突界面，完成双用户、断网、重试和大数据验收。

实施期间保留 MapSeek 工作区中已有的无关修改。完成前分别报告 GeoLedger、MapSeek 和真实浏览器的验证范围；仅离线单元测试通过不能替代联调验收。
