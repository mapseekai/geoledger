## 超时问题与修改

big.geojson 写入 PostGIS 用时 56.388 秒；原实现建立版本快照在 120.800 秒时触发 SQLSTATE 57014（statement timeout）。失败后验证：HEAD 保持 init 状态，数据集未注册，全表摘要未变，没有残留的跟踪触发器、tracking 记录或 repository marker，fsck 通过。

将 PostGIS 的语句超时改为可配置，默认仍为 120 秒。本轮显式使用 `SV_STATEMENT_TIMEOUT_SECS=900`，仅对事务内每条语句生效；锁等待超时仍为 5 秒。没有修改数据库全局配置、关闭触发器或改变对象编码。CLI 同时支持 `--statement-timeout-secs`；Rust API 为 `PostgisProvider::with_statement_timeout(Duration)`。配置拒绝 0、越界和非整毫秒时长。

本轮复用上次已完整导入的 big 测试表，并在新版本仓库中从初始快照重跑；重跑前再次比对全表摘要。后续命令全部经实际 CLI → Application → PostGIS 执行。

## 后续：字段功能与性能优化

本节记录同一天后续实现的结果，上文保留为优化前基线。使用独立克隆表 `sv_perf_70afd8742017.features` 和新仓库 `.reference/large-data-20260922/big_optimized_cacb7424/repo`，原测试表和输入文件保持不变。克隆后再次确认全表摘要与原基线一致。

### 普通数据操作

| 操作 | 优化前 | 优化后 |
|---|---:|---:|
| 初始版本导入 | 123.575 秒 | 71.190 秒 |
| 检测 10,000 条增量，输出 1 条 | 37.496 秒 | 2.281 秒 |
| 提交 10,000 条增量 | 119.086 秒 | 22.799 秒 |
| 切回 main | 40.410 秒 | 6.857 秒 |
| 切回 benchmark | 41.204 秒 | 5.672 秒 |
| 再切回 main | 39.246 秒 | 4.448 秒 |
| 快进合并 | 28.912 秒 | 2.985 秒 |
| revert | 53.211 秒 | 13.017 秒 |
| fsck | 498.086 秒 | 63.148 秒 |

两次版本操作处理相同的 10,000 条属性更新和 10 条带 Z 几何平移。优化后所有切换、合并、回退的全表摘要均匹配预期，最终 status 干净，fsck 返回成功。这里是完整重跑的各自仓库，v2 的结构对象与基线不同，不能把两轮 fsck 当成逐字节相同输入。

优化包括 dirty 主键批读、工作副本参数化批写、重复 schema 写入移出逐记录循环、压缩/解压上下文复用、解压按帧大小分配、预编译 SQL 复用及 SQLite 页缓存/mmap。对象哈希、EWKB 表达、数据库触发器、WAL、synchronous=FULL 及 journal 顺序均保留。

内存有明确权衡：初始导入 CLI 峰值 RSS 由 29.02 MiB 增至 110.91 MiB；增量提交由 109.91 MiB 增至 455.86 MiB；本轮切换/合并峰值约 501–506 MiB。RSS 包含映射到进程的数据库页，不等同于 Rust 堆大小。SQLite 主缓存目标上限 64 MiB、mmap 窗口 256 MiB；增量变化本身仍会内存化。不能称为固定低内存实现。新初始仓库大小 1,076,957,184 字节。

### 结构操作的额外瓶颈

第一次新增可空 text 字段并完整提交 483,268 行，用时 471.076 秒；随后填充 100 条值、提交用时 2.150 秒。2 秒进程采样显示，整表结构提交主要停留在 SQLite B-tree 页读取、换出和写入。修改结构会改变 record/v1 中的字段名/集合，导致全量重编码；初始导入的耗时不能代表这一场景。

基线采样完成后主动终止旧批写路径中的改名操作（265.905 秒，SIGTERM），这一步是取消而非通过或 SQL 超时。重开仓库验证 HEAD 仍为前一次提交、列名仍为 qa_note、100 条值仍为 '42'、status 干净。该检查仅覆盖扫描中断，不替代所有崩溃窗口测试。父目录 results.json 因主动终止记录 verified=false；成功续测使用独立 `schema_optimized/results.json`，避免覆盖原始记录。

针对这一瓶颈，结构扫描新增文件型临时对象表（16 MiB 页缓存），然后按对象哈希顺序写入正式库，减少已有大对象库的随机页写入。批写 savepoint 在原事务内部，失败回滚，不提前提交对象引用。需要额外临时磁盘空间，结构变更仍是整表操作。后续计时与完整恢复结果见续测记录。

续测的 `rename-field` 用时 179.996 秒、`alter-field-type` 用时 125.078 秒、`drop-field` 用时 137.522 秒，均成功。文本 '42' 转换为 integer 后，100 条值均为 42；删列后全表摘要恢复为最初基线。回到含 qa_note 的历史提交，用时 277.136 秒，字段与 100 条原值成功恢复。改名的旧路径被取消，不能据此计算精确加速倍数；各结构操作的数据内容和对象复用比例也不同。

再回到原始版本用时 270.106 秒，全表摘要再次匹配。直接 SQL 新增 qa_external 字段后，status 在 0.050 秒内报告结构变化与不完整行统计，避免为了预览而先读取全部几何。

外部新增字段的完整提交用时 215.722 秒，返回 rescanned_records=483268、changed_records=null。相比前面未做整表批写的新增字段 471.076 秒有所下降，但列名、历史对象库大小和缓存状态不完全相同，本次不把它当作严格 A/B 加速比。

历史 `diff --limit 1` 验证返回一条变化、total=483268、truncated=true，用时 257.190 秒。限量解码避免把所有几何装入变化数组，但精确计数仍遍历两个版本树；这是仍未解决的整表结构差异性能瓶颈，不能套用普通 dirty status 的 2.281 秒结果。

该历史 diff 峰值 RSS 为 260.78 MiB。最后一次从外部新增字段版本恢复原始结构用时 365.728 秒；随后全表摘要与初始数据一致，status 干净。同规模恢复会随对象库增长和缓存状态明显波动，不能保证固定延迟。

### 最终结果

续测 `schema_optimized/results.json` 返回 **verified=true**。最终 fsck 校验 **4,109,530 个对象**，返回 ok=true，用时 **452.587 秒**，峰值 RSS 307.45 MiB。最终仓库文件合计 **4,296,130,560 字节（约 4.00 GiB）**，从初始约 1.00 GiB 明显增长；当前无 GC，字段名编码导致的完整历史记录复制是实际空间成本。

最终 main 已回到结构变化前的提交，可达图为 4 个提交、3 个快照；字段操作期间的提交仍保留在对象库中，可按逐步日志中的 ID 或 reflog 查看。fsck 的对象校验覆盖全部对象，不仅是当前可达记录。小规模集成测试另覆盖含结构历史分支的图与记录校验。

最终 fsck 的采样显示已进入数据树遍历和记录校验阶段，主要等待对象随机读取。它的对象量、对象库大小均大于普通数据阶段，不能将 452.587 秒直接与上表的 63.148 秒视为同输入退化测试；同时，这证明扩大历史库后的遍历仍有性能瓶颈。
